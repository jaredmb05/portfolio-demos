# Decisions

Choices already made, and why. **Don't reopen these without a new reason.** Add new ones at the top.

| # | Decision | Why | Revisit if |
|---|---|---|---|
| D22 | **Production deploys through GitHub → Netlify** (branch `main`, a base directory per app; each folder's `netlify.toml` publishes it as is). Still **no build step** (D3 stands). This repo has no deploy configuration and is never deployed from here. | The owner asked for push-to-deploy instead of drag-and-drop; it also stops the "dragged the wrong folder onto the wrong site" mistake. | Deploy credits run short (then add an ignore rule so a site deploys only when its own folder changed), or GitHub access is lost (drag-and-drop still works). |
| D21 | **No concession guardrails**: staff can enter any concession on any unit, on the iPad and the Desk. Production tried guardrails and took them out: v1.20 added limits per unit size with building exceptions, a credit cap, a "rule wins over the showsheet" flag and a manager override; a lock to units that have a showsheet concession came next; v1.21 removed all of it the same day. | Unadvertised word-of-mouth and back-pocket offers aren't on the showsheet, the owner decides case by case what staff may offer, and a lock got in the way of planning a tour. The backlog items for an approved-incentives check and for confirming every override were dropped for the same reason. | Wrong concessions become a real problem; then design limits the iPad never displays. |
| D20 | **The team schedule is Desk-only**: the iPad shows no rotation, who's in / out, Mark out / back in, next up or wait estimates, and its name pickers list the whole team A to Z. | The iPad is held by the assistant already chosen for the tour; dispatching (who's free, who's next, how long the wait is) is the front desk's job (owner's decision). Extends D17. | Assistants start assigning walk-ins themselves from the iPads. |
| D19 | **A per-tour override changes amounts, never the broker rule.** Both apps can override the prospect's concession, the broker OP (iPad: only when "Touring with a broker" is checked) and a credit; only the Desk has the AND/OR selector and the lease-term field, and its email must follow its own selector. Broker rules: no broker → the prospect's incentive only, never mention the OP; **AND** → the broker gets the OP *and* the prospect's net effective rent is shown; **OR** → the OP to the broker, the prospect's concession and net rent only if the broker waives it. Net effective uses the unit's actual lease term, read from the incentive text ("on 24-Month Lease"; 12 months when none is written); `½` reads as `1/2`, and "1 1/2" or "1½" is 1.5 months; text mixing "and" and "OR" is an OR incentive. A credit is quoted next to the rent and never included in the net effective. When the Desk's "Other concession" has both free months and an OP, the "OP only" / "No broker" checkboxes follow its AND/OR selector. | Follow-up emails go to both the prospect and the broker, so the email has to be right for both. Owner's rulings, 2026-10-06 (AUDIT.md §11, including the follow-up rulings). **Status:** fixed in Phase 3; `tests/unit/money-rulings.test.js` asserts each rule. | A credit gets an "include in net effective" toggle (BACKLOG). |
| D18 | **ES modules, still no build step.** Each app is `index.html` + `styles.css` + `js/` modules; code both apps use lives once in `apps/shared/` (pricing, rotation, availability, wait estimate and panel, unit options, dates, requirements, tokens.css). The Desk's money, ordering and date rules sit in `apps/desk/js/rules/` as pure functions (no DOM, Firebase or app state), so tests import them directly. The HTML's inline `on*` handlers still call functions by name, so each `main.js` puts those on `window`. Variables several modules change live in each app's `state.js`. | D2's copies had to be diffed by hand on every change, and the rules couldn't be unit-tested inside one big script. Browsers load modules natively, so there is still no toolchain to maintain. Trade-offs: modules need http (`npx serve`), not `file://`; the deploy unit is the `apps/` folder (one site, `/desk/` and `/tour-companion/`) instead of two drag-and-drop folders; the iPad service worker must list every module. | A bundler is introduced, or the inline handlers move to delegated listeners (then the `window` bridge goes). |
| D17 | *(Updated by D20: the iPad has no next up, busy labels or start warning.)* **Desk only: "next up" skips anyone on a tour right now**: first in rotation order who is in today and has no unfinished tour started today. Busy people are labelled "back ~time"; starting with one asks first. Rotation counts and order (`rotationStats`) are unchanged. | The fairness pick could name someone mid-tour, and the Desk preselected them on waiting rows, so a walk-in could be started with an assistant who was out on the floor. Uses the same busy rule as the wait estimate. The Desk is where walk-ins are assigned. | Staff want "next up" to mean pure fairness order again. |
| D16 | *(Updated by D18: the token block is now one file, `apps/shared/tokens.css`, linked first by both apps. The wait-panel `.wp-*` rules stay in each app's stylesheet, because they sit mid-cascade and moving them would change a hover style.)* One **shared design-token block** (colors, motion, `.pill` / `.flag` styles) copied **byte-identical** into both apps, between `SHARED TOKENS` markers; each app keeps its own size tokens (Desk denser, iPad 44pt touch). Desk corners stay square, iPad rounded. | The two apps had drifted (same "Inspection" tag in two colors, different status words). No build step means no shared stylesheet file (D3), so the block is copied and diffed like the shared logic (D2). | A build step or a shared CSS file on Netlify is introduced. |
| D15 | Build stamps become **version numbers** (`v1.19`, `v1.20`…) starting with the next deploy | The date-style labels ran ahead of the calendar ("2026-10-18" shipped Oct 4) and read like release dates. Real dates would make the next build look older than the current one. | Never — mapping: Desk 2026-10-18 = v1.18, iPad 2026-10-15b = v1.15. |
| D14 | Future Move-Ins stores **no email or phone** | Collections are world-readable (no logins). The leasing manager finds the original email in Outlook by first name + tour date. | Sign-in is added to the apps. |
| D13 | Future Move-Ins alerts = **in-Desk badge + optional Outlook .ics**, not email | A real email alert needs a server; .ics import works without IT (Outlook publishing is blocked by the company's Microsoft 365 admin). | Desk badge + .ics prove insufficient. |
| D12 | While Dropbox sync is on, **Dropbox is the only source** (Upload/Publish/Clear hidden) | A stale manual upload + publish would override everyone until the next Dropbox edit. | Never — turn sync off in Settings to go manual. |
| D11 | Dropbox links are **"Anyone with the link"** and stored in Firestore | The Desk must download them without a login. Links are long/random; only live in settings. | A server-side fetch (Netlify function) is added. |
| D10 | Dropbox floor plans **not** shared via public folder links | A folder link lets prospects browse every floor plan. Per-file links only. | — |
| D9 | No self-hosted floor plan site | ~900 MB, needs CLI deploys, and must be re-uploaded whenever Dropbox changes. | Browsing concern changes or volume drops. |
| D8 | Desk loads **30 days / 800 tours**; iPad **10 days / 400** | The old 80-tour cap hid check-ins after a few days. ~125 tours/week. | Firebase read usage warnings. |
| D7 | Every Desk follows the published showsheet; **newest wins** | Desks kept stale per-computer uploads. A local unpublished upload newer than the last publish is protected. | — |
| D6 | iPad saves **merge**; iPad adopts remote changes to the open tour unless it has unsaved typing | A full overwrite erased Desk-owned fields (finish, follow-up/check-in sent). | — |
| D5 | App updates show **only on reload** (no forced reload) | A forced reload would wipe an email in progress. An "update available" banner is in the backlog. | — |
| D4 | No sign-in on either app | Front-desk/iPad speed; staff turnover. Trade-off: world-readable data, client-side PIN. | Any personal data beyond the optional tour email is needed. |
| D3 | *(Original design, updated by D18: still CDN libraries and no build step, but no longer one file per app.)* Single-file HTML, CDN libraries, **no build step** | The owner deploys by drag-and-drop and edits by hand; no toolchain to maintain. | Moving to Git-based Netlify deploys with a build. |
| D2 | *(Superseded by D18.)* Shared rotation logic is **duplicated** in both apps (kept identical) | No build step means no shared module. | A build step is introduced. |
| D1 | Red fill on the unit cell = **APP PENDING** | It's how the showsheet is maintained; systematic, not manual. | Showsheet format changes. |
